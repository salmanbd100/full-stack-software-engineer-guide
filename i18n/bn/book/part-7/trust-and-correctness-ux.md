# বিশ্বাস, নির্ভুলতা ও Failure State {#ch-trust-and-correctness-ux}

> এমন system-এর জন্য interface design করুন, যেটা সাধারণত ঠিক, মাঝে মাঝে ভুল, দুই ক্ষেত্রেই সমান আত্মবিশ্বাসী, আর যার ব্যর্থতা স্বাভাবিক traffic-এরই অংশ।

**এই অধ্যায়ে:** মাপা বিশ্বাস আর যাচাই করা যায় এমন citation · confidence score কেন বিভ্রান্ত করে · accept করার আগে edit, আর undo · ছয়টি failure state · অর্ধেক উত্তর রেখে দেওয়া আর ভদ্রভাবে মান নামানো

## 💡 মূল ধারণা

প্রথম ঝোঁক থাকে AI feature-কে বিশ্বাসযোগ্য মনে হওয়ার মতো করা। লক্ষ্যটা ভুল। **লক্ষ্য হলো মাপা বিশ্বাস: feature যত
ঘন ঘন ঠিক, user মোটামুটি তত ঘন ঘনই সেটা বিশ্বাস করবেন।** বেশি বিশ্বাস মানে ভুল উত্তর যাচাই ছাড়াই চলে যায়। কম
বিশ্বাস মানে feature কেউ ব্যবহার করে না। দুটির মধ্যে দামি ভুলটা হলো বেশি বিশ্বাস।

Model কতটা আত্মবিশ্বাসী, তা থেকে উত্তরটা কতটা ঠিক, কিছুই বোঝা যায় না। তথ্যটা retrieve করা হোক বা বানানো, গদ্য একই রকম
সাবলীল থাকে, আর user সাবলীলতাকে দক্ষতা বলে ধরে নেন। তাই text যা দিতে পারে না, interface-কে সেটা দিতে হয়: **এটা
কোথা থেকে এলো, আর user কত সহজে সেটা যাচাই করতে পারেন।**

কিছু ভুল হলেও একই সততা লাগে। AI feature-এ **ব্যর্থতা স্বাভাবিক কাজেরই একটি অবস্থা**: refusal রোজ ঘটে, আর যে সপ্তাহে
feature সফল হয়, rate limit আসে ঠিক সেই সপ্তাহেই।

> User-কে উত্তরটা বিশ্বাস করতে বলবেন না। দুই সেকেন্ডে যাচাই করার একটি উপায় দিন। ব্যর্থ হলে যা আছে তা রেখে দিন, কী
> হয়েছে বলুন, আর পরের পদক্ষেপ সহজ করে দিন।

## কীভাবে কাজ করে

### যাচাই করা যায় এমন citation

Citation-এর দাম আছে শুধু তখনই, যদি সেটা যাচাই করা যায়, আর যাচাই করা হয়েছে।

| ❌ দুর্বল | ✅ শক্ত |
| --- | --- |
| "Documentation অনুযায়ী…" | Retrieve করা ঠিক সেই passage-এর inline link |
| শেষে source-এর একটি তালিকা | নির্দিষ্ট দাবিটার সঙ্গে জুড়ে দেওয়া citation |
| Model নিজে যে citation লিখেছে | Retrieve করা chunk id থেকে resolve করা citation |

শেষ row-টা নির্ভুলতার একটি control, শুধু সৌজন্য নয়। Documentation assistant-এ model একটি chunk id দেয় আর server সেটা
resolve করে। তখন বানানো citation render হতেই পারে না, কারণ সেই id কখনো retrieve হয়নি। এই check-এর কোনো খরচ নেই, আর
grounded assistant-এর সবচেয়ে ক্ষতিকর ব্যর্থতাটা এতেই ধরা পড়ে।

কোথায় বসছে, সেটাও জরুরি। বাক্যের পাশে থাকা citation লোকে যাচাই করে। নিচে দেওয়া source-এর তালিকা লোকে উপেক্ষা করে,
অথচ তাতেও বিশ্বাস বাড়ে। মানে কঠোরতার চেহারাটুকু আছে, ভেতরে কিছু নেই।

### Confidence score সাধারণত বিভ্রান্ত করে

"87% নিশ্চিত" পড়তে একটি মাপের মতো লাগে। আসলে সেটা মাপ, শুধু যদি calibrate করা থাকে: অনেক উত্তরের মধ্যে যেগুলোকে 87%
বলা হয়েছে, সেগুলো মোটামুটি 87% সময় ঠিক। Model নিজের নির্ভরযোগ্যতা জানাতে মোটেই ভালো নয়।

| Score-এর বদলে | দেখান |
| --- | --- |
| "87% নিশ্চিত" | কোন source ব্যবহার করেছে, বা কোনো source পায়নি এই কথাটা |
| "কম নিশ্চিত" | "Documentation-এ এটা খুঁজে পাইনি" |

**সৎ বিকল্প হলো grounding।** "এটা এসেছে retrieve করা তিনটি passage থেকে" আর "এটা এসেছে model-এর নিজের জ্ঞান থেকে",
এই দুটি অবস্থা আপনার code নিজেই ঠিক করতে পারে। দুটিই user-কে সত্যি কিছু জানায়।

### Accept করার আগে edit, আর undo

যে output কোথাও কিছু লেখে, সেটা বসার আগে user-এর হাত ঘুরে আসা উচিত।

**Flow-টা, যেখানে স্পষ্ট accept-ই সেই ধাপ যেটা বাদ দেওয়া যাবে না:**

```text
Generate  →  Show as an editable draft  →  User edits  →  Explicit accept  →  Apply
```

নিজে থেকে apply করে দেওয়াতেই AI feature চিরদিনের মতো user হারায়। চুপচাপ একটি ভুল edit যতটা বিশ্বাস নষ্ট করে, বিশটি
ভালো suggestion ততটা গড়তে পারে না। এরপর user-কে সবকিছু যাচাই করতে হয়, যেটা নিজে কাজটা করার চেয়েও বেশি খাটুনি।

| ভুল output-এর পরিণাম | Pattern |
| --- | --- |
| তুচ্ছ আর চোখে পড়ে | Apply করুন, undo-সহ |
| দামি বা সহজে চোখে পড়ে না | Draft, review, স্পষ্ট accept |
| ফেরানো যায় না | কী ঘটবে তার নাম বলে স্পষ্ট confirmation |
| অন্য মানুষের ওপর প্রভাব পড়ে | Review, সবসময় |

ব্যবহার বাড়াতে undo নির্ভুলতার চেয়েও বেশি কাজ করে, কারণ ভুলের দাম বদলে দেয়। Apply করার সময় এটা দেখান, পুরো
operation undo করুন, আর আগের version রেখে দিন।

### Disclaimer-এর অভিনয় ছাড়া সততা

প্রতিটি message-এর নিচে "AI ভুল করতে পারে" লিখে দিলে দায়টা user-এর ঘাড়ে যায়, অথচ তাঁর কোনো সাহায্য হয় না। এটা
একবার পড়া হয়, তারপর আর কখনো নয়। দাবির পাশে citation, generate করা content-এ চোখে পড়ার মতো চিহ্ন, আর সত্যি হলে
সোজাসুজি "docs-এ পাওয়া যায়নি", এগুলো অনেক বেশি কাজ করে।

> ⚠️ প্রতিটি বাক্যে দ্বিধা জুড়ে দিলে ("মনে হচ্ছে যে", "আপনি হয়তো চাইতে পারেন") signal-টাই নষ্ট হয়। সবকিছুতে দ্বিধা থাকলে
> সত্যিই অনিশ্চিত উত্তর আর আত্মবিশ্বাসী উত্তর দেখতে হুবহু এক রকম লাগে।

### ছয়টি failure state

| অবস্থা | কারণ | Screen-এ যা লাগবে |
| --- | --- | --- |
| **Refusal** | Policy, scope, বা আপনার guardrail | কী প্রত্যাখ্যান করা হলো, আর কী *সম্ভব* |
| **Timeout** | Model বা retrieval ধীর | যতটুকু stream হয়েছে, সঙ্গে retry |
| **Truncation** | Output-এর বরাদ্দ শেষ | অর্ধেক উত্তর, চিহ্ন দেওয়া, সঙ্গে "continue" |
| **Rate limit** | Provider-এর বা আপনার নিজের quota | কখন আবার চলবে, আর অর্ধেক উত্তর |
| **খালি retrieval** | Corpus-এ কিছুই মেলেনি | "Docs-এ নেই", আর docs আসলে কী কী নিয়ে |
| **Provider outage** | যার ওপর নির্ভর করা, সেটাই বন্ধ | সৎভাবে জানান যে পাওয়া যাচ্ছে না; ভাবার ভান করবেন না |

দুটিকে প্রায়ই ভুল জায়গায় ফেলা হয়। খালি retrieval-কে ব্যর্থতা ধরা হয়, অথচ এটা একটি সৎ আর কাজের উত্তর। Truncation
প্রায়ই ধরাই পড়ে না: `finishReason: 'length'` আসে HTTP 200-এর সঙ্গে, তাই অর্ধেক বাক্য সম্পূর্ণ উত্তর হিসেবে render হয়।

### অর্ধেক উত্তর কখনো ফেলে দেবেন না

**Stream ভেঙে গেলে user যা দেখেন:**

```text
❌  [8 seconds of streamed text]  →  cleared  →  "Something went wrong"
✅  [8 seconds of streamed text]  →  kept, marked incomplete  →  "Connection lost — continue?"
```

অর্ধেক উত্তরটাতেই প্রায়ই user-এর দরকারের বেশিরভাগ থাকে, সেটা পড়াও হয়ে গেছে, দামও দেওয়া হয়ে গেছে। রেখে দিন, অসম্পূর্ণ
বলে চিহ্ন দিন, আর যেখানে থেমেছিল সেখান থেকে continue করার সুযোগ দিন।

### এমন error, যা পরের পদক্ষেপ দেখায়

| ❌ Message | ✅ Message |
| --- | --- |
| "কিছু একটি গোলমাল হয়েছে" | "Model-এর বেশি সময় লেগেছে। যতটুকু বানিয়েছে, এই যে — আবার চেষ্টা করবেন?" |
| "Error 429" | "এই মুহূর্তে অনেক বেশি request। সাধারণত মিনিটখানেকের মধ্যে ঠিক হয়ে যায়।" |
| "এ ব্যাপারে আমি সাহায্য করতে পারব না" | "আমি শুধু product documentation নিয়ে কাজ করি। Account-এর প্রশ্নের জন্য support-এ যোগাযোগ করুন।" |

ভালো message-এর তিনটি অংশ: **কী হয়েছে, retry করে লাভ আছে কি না, আর আর কী চেষ্টা করা যায়।** Model-এর জন্য tool-এর
error message যে নিয়মে লেখা হয়, এটা সেই নিয়মই, শুধু মানুষের জন্য লেখা। দেখুন
[Chapter ?? — Tool Calling ও Tool Surface](#ch-tool-calling)।

ব্যর্থ feature-এর উচিত ফিরে যাওয়া সেখানে, feature আসার আগে product যা করত। AI search ব্যর্থ হলে keyword-এর result
দেখান। Summary না থাকলে পুরো document দেখান। **Inline-এ সাহায্য করা feature-এর ব্যর্থতা চোখেই পড়া উচিত নয়।** যে editor
একটি suggestion না পেয়ে error box দেখায়, সেটা suggestion না থাকার চেয়েও খারাপ।

### বিরক্ত না করে retry

অল্পক্ষণের যে ব্যর্থতায় কোনো আংশিক content আসেনি, সেটা একবার, চুপচাপ retry করুন। মানে একটি 500, বা প্রথম token-এর
আগেই timeout। Refusal বা content filter কখনো নিজে থেকে retry করবেন না। এটা একটি সিদ্ধান্ত, outage নয়, আর আবার খরচ হয়।
হাতে retry করলে প্রশ্নটা থেকে যেতে হবে। পরপর তিনবার ব্যর্থ হলে বলে দিন যার ওপর নির্ভর করা, সেটা বন্ধ।

> ⚠️ যে streamed request ইতিমধ্যে token দিয়েছে, সেটা নিজে থেকে retry করলে দুবার টাকা কাটে, আর দুটি আলাদা উত্তর জোড়া
> লেগে যেতে পারে। হয় আংশিক অবস্থা থেকে continue করুন, নয়তো পরিষ্কারভাবে নতুন করে শুরু করুন, কিন্তু দুটি একসঙ্গে নয়।

## কখন ব্যবহার করবেন

| Feature | বিশ্বাসের design | অগ্রাধিকারের failure state |
| --- | --- | --- |
| আপনার docs থেকে grounded উত্তর | Chunk id থেকে resolve করা inline citation | খালি retrieval আর refusal |
| Generate করা draft | Accept করার আগে edit, সবসময় | Timeout, draft রেখে দিয়ে |
| বের করে আনা form field | ভরে দিন, generate করা বলে চিহ্ন দিন, undo রাখুন | চুপচাপ হাতে লেখার ব্যবস্থায় ফিরে যাওয়া |
| লম্বা summary | প্রতিটি পয়েন্ট তার source-এ link করুন | Truncation আর continue |
| Inline editor-এর suggestion | চোখে পড়ার মতো চিহ্ন | চুপচাপ ব্যর্থতা; কখনো বাধা দেবেন না |
| বেশি traffic-এর consumer feature | সোজাসাপ্টা উত্তর, ঢালাও disclaimer নয় | Rate limit, স্পষ্ট অপেক্ষার সময়সহ |

প্রথম screen-এর আগেই failure state design করুন। এখানে এগুলো বিরল নয়, তাই শেষে design করা মানে product-এর বেশিরভাগটাই
শেষে design করা।

## সাধারণ ভুল

**❌ Confidence-এর শতাংশ দেখানো**

> পড়তে মাপের মতো লাগে, অথচ calibrate করা নয়। তার বদলে grounding দেখান।

**❌ Generate করা পরিবর্তন নিজে থেকে apply করে দেওয়া**

> চুপচাপ একটি ভুল edit যতটা বিশ্বাস নষ্ট করে, বিশটি ভালো suggestion ততটা গড়তে পারে না।

**❌ ব্যর্থ হলে stream হওয়া text মুছে ফেলা, বা কেটে যাওয়া উত্তরকে সম্পূর্ণ হিসেবে render করা**

> প্রথমটায় user যা পড়ে ফেলেছেন আর আপনি যার দাম দিয়ে ফেলেছেন, সেটা ফেলে দেওয়া হয়। দ্বিতীয়টায় অর্ধেক বাক্য চলে যায়,
> কারণ `length` finish আসে HTTP 200-এর সঙ্গে, আর কিছুই throw করে না।

**✅ Retrieve করা chunk id থেকে citation resolve করুন, আর ব্যর্থ হলে কী হয়েছে বলুন**

> বানানো citation render হতেই পারে না, আর পরের পদক্ষেপ দেখানো message একটি কানাগলিকে কাজের সুযোগে বদলে দেয়।

## 🔑 মূল শিক্ষা

- লক্ষ্য মাপা বিশ্বাস, সর্বোচ্চ বিশ্বাস নয়, আর দামি ব্যর্থতা হলো বেশি বিশ্বাস।
- দাবির সঙ্গে জোড়া আর chunk id থেকে resolve করা citation লোকে যাচাই করে, আর confidence score শুধু দেখতে মাপের মতো।
- যা কিছু লেখে, সেটা হবে স্পষ্ট accept-সহ draft, আর ব্যবহার বাড়াতে undo নির্ভুলতার চেয়েও বেশি কাজ করে।
- Refusal, timeout, truncation আর rate limit স্বাভাবিক traffic, তাই আংশিক output রেখে দিন আর `length` finish আলাদা করে ধরুন।
- অল্পক্ষণের ব্যর্থতা একবার চুপচাপ retry করুন, refusal কখনো নয়, আর আংশিক stream-এর ওপরে তো কখনোই নয়।

## Interview-এর প্রশ্ন

**Q: উত্তরটা ভুল হতে পারে, user-কে এটা কীভাবে দেখান?**

বলে দিয়ে নয়, যাচাই করাটা সহজ করে দিয়ে। Citation বসে দাবির পাশে, আর retrieve করা ঠিক সেই passage-এ link করে। Grounding
সৎভাবে জানানো হয়, আর সাধারণ জ্ঞান থেকে সাবলীল উত্তরের বদলে আসে "এটা খুঁজে পাইনি"। প্রতিটি message-এর নিচে disclaimer
দায়টা সরিয়ে দেয়, কিন্তু কাউকে কিছু করার উপায় দেয় না।

**Q: Confidence score দেখান না কেন?**

কারণ দেখতে মাপের মতো, অথচ মাপ নয়। অনেক case জুড়ে যাচাই করে যদি না দেখা যায় যে 80% বলা উত্তরগুলো মোটামুটি 80% সময়
ঠিক, তাহলে এটা শুধু model-এর বানানো একটি value। আরও খারাপ, নিখুঁত দেখতে সংখ্যা ঝাপসা কথার চেয়ে বেশি বিশ্বাস জাগায়,
তাই user-কে বেশি বিশ্বাসের দিকে ঠেলে দেয়।

**Q: Generate করা পরিবর্তন কখন নিজে থেকে apply করবেন?**

শুধু তখন, যখন ভুল ফল তুচ্ছ, সঙ্গে সঙ্গে চোখে পড়ে, আর undo হাতের কাছেই। দামি, সহজে চোখে পড়ে না, ফেরানো যায় না, বা
অন্য মানুষের ওপর প্রভাব ফেলে, এমন সবকিছু যায় স্পষ্ট accept-সহ draft দিয়ে। চুপচাপ একটি ভুল edit হলেই user প্রতিটি
output যাচাই করতে শুরু করেন, আর সেই ক্ষতি আর পূরণ হয় না।

**Q: Stream-এর মাঝপথে request rate limit-এ আটকে গেল। User কী দেখবেন?**

যতটুকু text আগেই এসেছে, সেটা, রেখে দেওয়া আর অসম্পূর্ণ বলে চিহ্ন দেওয়া। সঙ্গে সোজা ভাষায় কী হয়েছে আর মোটামুটি কখন
আবার চলবে। Pane মুছে সাধারণ একটি error দেখানো চলবে না, তাতে আগেই পড়া আর দাম দেওয়া content ফেলে দেওয়া হয়। মূল
পদক্ষেপ হলো আংশিক অবস্থা থেকে continue করা, আর নতুন করে generate করা বিকল্প।

**Q: কখন নিজে থেকে retry করেন?**

একবার, চুপচাপ, অল্পক্ষণের এমন ব্যর্থতায় যেখানে কোনো আংশিক content আসেনি: একটি 500, overload, প্রথম token-এর আগেই
timeout। Refusal বা content filter-এ নয়, কারণ সেগুলো একই ফল দেয় আর আবার টাকা কাটে। যে stream ইতিমধ্যে token দিয়েছে,
তার ওপরেও নয়, কারণ তাতে দুবার টাকা কাটে আর দুটি উত্তর জোড়া লেগে যেতে পারে।

**Q: Failure state আগে design করেন কেন?**

কারণ এই ধরনের feature-এ এগুলো বিরল নয়, তাই শেষে design করা মানে product-এর বেশিরভাগটাই শেষে design করা। নির্দিষ্ট
scope-এর assistant-এ refusal আর খালি retrieval রোজ ঘটে। আগে এগুলোর খসড়া করলে একটি প্রশ্নের স্পষ্ট উত্তরও দিতে হয়:
চমকপ্রদ কাজটা করতে না পারলে feature কী করে?

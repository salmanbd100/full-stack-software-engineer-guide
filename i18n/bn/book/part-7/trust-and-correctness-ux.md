# বিশ্বাস, নির্ভুলতা ও Failure State {#ch-trust-and-correctness-ux}

> এমন একটি system-এর জন্য interface design করুন, যেটা সাধারণত ঠিক, কখনো কখনো ভুল, দুই ক্ষেত্রেই সমান আত্মবিশ্বাসী, আর যার ব্যর্থতা স্বাভাবিক traffic-এরই অংশ।

**এই অধ্যায়ে:** calibrated trust আর যাচাই করা যায় এমন citation · confidence score কেন বিভ্রান্ত করে · accept করার আগে edit আর undo · ছয়টি failure state · আংশিক উত্তর রেখে দেওয়া আর ভদ্রভাবে degrade করা

## 💡 মূল ধারণা

স্বাভাবিক প্রবৃত্তি হলো একটি AI feature-কে বিশ্বাসযোগ্য মনে করানো। লক্ষ্যটা ভুল। **আসল লক্ষ্য calibrated trust: user
এটাকে মোটামুটি ততবারই বিশ্বাস করবেন, যতবার এটা ঠিক।** অতিরিক্ত বিশ্বাস মানে ভুল উত্তর যাচাই ছাড়াই চলে যায়। কম বিশ্বাস
মানে কেউ feature-টা ব্যবহারই করে না। দুটির মধ্যে অতিরিক্ত বিশ্বাসটাই দামি।

একটি model-এর আত্মবিশ্বাস তার নির্ভুলতা সম্পর্কে কিছুই বলে না। তথ্যটা retrieve করা হোক বা বানানো, গদ্য সমান সাবলীল,
আর user-রা সাবলীলতাকে দক্ষতা হিসেবে পড়েন। তাই text যা দিতে পারে না, interface-কে সেটা দিতে হবে: **এটা কোথা থেকে এসেছে,
আর user কত সহজে এটা যাচাই করতে পারেন।**

কিছু ভুল হলেও একই সততা খাটে। একটি AI feature-এ **ব্যর্থতা কাজ চলার একটি স্বাভাবিক state**: refusal রোজই ঘটে, আর
feature সফল হওয়ার সপ্তাহেই rate limit এসে হাজির হয়।

> User-কে উত্তরটা বিশ্বাস করতে বলবেন না। তাঁকে দুই সেকেন্ডে সেটা যাচাই করার একটি উপায় দিন। ব্যর্থ হলে যা আছে তা রেখে
> দিন, কী হয়েছে বলুন, আর পরের পদক্ষেপ সহজ করুন।

## কীভাবে কাজ করে

### যাচাই করা যায় এমন citation

একটি citation-এর মূল্য তখনই, যখন সেটা যাচাই করা যায়, আর যাচাই করা হয়েছে।

| ❌ দুর্বল | ✅ শক্তিশালী |
| --- | --- |
| "Documentation অনুযায়ী…" | Retrieve করা ঠিক সেই অংশের একটি inline link |
| শেষে একটি source-এর তালিকা | নির্দিষ্ট দাবিটির সাথে জোড়া একটি citation |
| Model-এর নিজে বানানো একটি citation | Retrieve করা একটি chunk id থেকে resolve করা একটি citation |

শেষ সারিটা নির্ভুলতার একটি control, সৌজন্য নয়। Documentation assistant-এ model একটি chunk id বের করে, আর server সেটা
resolve করে। তখন একটি বানানো citation render হতেই পারে না, কারণ সেই id কখনো retrieve করা হয়নি। যাচাইটার কোনো খরচ নেই,
আর এটা একটি grounded assistant-এর সবচেয়ে ক্ষতিকর failure ধরে।

কোথায় বসানো হচ্ছে, সেটাও গুরুত্বপূর্ণ। নিজের বাক্যের পাশে থাকা citation যাচাই হয়। নিচে একটি source-এর তালিকা উপেক্ষিত
হয়, অথচ তবু বিশ্বাস বাড়ায়। এটা কঠোরতার চেহারা, ভেতরে কিছু ছাড়াই।

### Confidence score সাধারণত বিভ্রান্ত করে

"87% confident" একটি পরিমাপের মতো পড়ায়। এটা পরিমাপ কেবল তখনই, যখন এটা calibrated: অনেক উত্তরের মধ্যে যেগুলোকে 87%
চিহ্নিত করা হয়েছে, সেগুলো মোটামুটি 87% সময় ঠিক। Model-রা নিজেদের নির্ভরযোগ্যতা জানাতে কাঁচা।

| Score-এর বদলে | কী দেখাবেন |
| --- | --- |
| "87% confident" | যে source-গুলো ব্যবহার করেছে, অথবা কিছুই না পাওয়ার একটি note |
| "Low confidence" | "Documentation-এ আমি এটা খুঁজে পাইনি" |

**Grounding-ই সৎ প্রতিনিধি।** "এটা এসেছে তিনটি retrieve করা অংশ থেকে" আর "এটা এসেছে model-এর নিজের জ্ঞান থেকে", এই দুটি
state আপনার code নির্ধারণ করতে পারে। দুটিই user-কে সত্যি কিছু বলে।

### Accept করার আগে edit, আর undo

যে output কোথাও লেখে, সেটা জায়গামতো পৌঁছানোর আগে user-এর হাত ঘুরে যাওয়া উচিত।

**Flow-টি, যেখানে স্পষ্ট accept সেই ধাপ, যেটা কোনোভাবেই বাদ দেওয়া যাবে না:**

```text
Generate  →  Show as an editable draft  →  User edits  →  Explicit accept  →  Apply
```

নিজে থেকে apply করে দেওয়াতেই AI feature-গুলো চিরতরে user হারায়। নীরবে করা একটি ভুল edit যতটা বিশ্বাস নষ্ট করে, বিশটি
ভালো suggestion ততটা গড়ে না। এরপর user-কে সবকিছু যাচাই করতে হয়, যেটা নিজে কাজটা করার চেয়েও বেশি খাটুনি।

| ভুল output-এর পরিণাম | Pattern |
| --- | --- |
| তুচ্ছ আর চোখে পড়ে | Apply করুন, undo-সহ |
| দামি বা চোখে পড়া কঠিন | Draft, review, স্পষ্ট accept |
| ফেরানো যায় না | কী ঘটবে তার নাম বলে স্পষ্ট confirmation |
| অন্য মানুষকে প্রভাবিত করে | Review, সবসময় |

গ্রহণযোগ্যতা বাড়াতে undo নির্ভুলতার চেয়েও বেশি করে, কারণ এটা একটি ভুলের দাম বদলে দেয়। Apply করার সময় এটা দেখান,
পুরো operation undo করুন, আর আগের version রেখে দিন।

### Disclaimer-এর নাটক ছাড়া সততা

প্রতিটি message-এর নিচে "AI ভুল করতে পারে" দায়টা user-এর ঘাড়ে চাপায়, অথচ তাঁকে কোনো সাহায্য করে না। এটা একবার পড়া হয়,
আর কখনো নয়। দাবির পাশে একটি citation, generate করা content-এ চোখে পড়ার মতো চিহ্ন, আর সত্যি হলে সোজাসুজি "docs-এ পাওয়া
যায়নি", এগুলো সবই বেশি কাজ করে।

> ⚠️ প্রতিটি বাক্যে দ্বিধা মেশালে ("মনে হচ্ছে যে", "আপনি হয়তো চাইতে পারেন") সংকেতটাই নষ্ট হয়। সবকিছুতে দ্বিধা থাকলে,
> সত্যিই অনিশ্চিত উত্তরটা দেখতে হুবহু আত্মবিশ্বাসী উত্তরের মতো।

### ছয়টি failure state

| State | কারণ | Screen-এ যা দরকার |
| --- | --- | --- |
| **Refusal** | Policy, scope, বা আপনার guardrail | কী প্রত্যাখ্যান করা হয়েছে, আর কী *সম্ভব* |
| **Timeout** | Model বা retrieval ধীর | যা stream হয়েছে, সাথে retry |
| **Truncation** | Output-এর বরাদ্দ শেষ | আংশিক উত্তর, চিহ্নিত, সাথে "continue" |
| **Rate limit** | Provider বা আপনার নিজের quota | কখন কাজ করবে, আর আংশিক উত্তর |
| **খালি retrieval** | Corpus-এ কিছুই মেলেনি | "Docs-এ নেই", আর docs কী কী নিয়ে আছে |
| **Provider outage** | Dependency বন্ধ | সৎভাবে জানানো যে পাওয়া যাচ্ছে না; ভাবছে বলে ভান করবেন না |

দুটি প্রায়ই ভুল শ্রেণিতে পড়ে। খালি retrieval-কে failure ধরা হয়, অথচ এটা একটি সৎ, কাজের উত্তর। Truncation প্রায়ই ধরা
পড়ে না: `finishReason: 'length'` আসে HTTP 200-এর সাথে, তাই অর্ধেক একটি বাক্য সম্পূর্ণ উত্তর হিসেবে render হয়।

### আংশিক উত্তর কখনো ফেলে দেবেন না

**একটি stream ভাঙলে user যা দেখেন:**

```text
❌  [8 seconds of streamed text]  →  cleared  →  "Something went wrong"
✅  [8 seconds of streamed text]  →  kept, marked incomplete  →  "Connection lost — continue?"
```

আংশিক উত্তরটা প্রায়ই user-এর যা দরকার ছিল তার বেশিরভাগ, যেটা ইতিমধ্যে পড়া আর ইতিমধ্যে দাম দেওয়া। এটা রেখে দিন,
অসম্পূর্ণ বলে চিহ্নিত করুন, আর যেখানে থেমেছে সেখান থেকে চালিয়ে যাওয়ার প্রস্তাব দিন।

### এমন error, যা পরের পদক্ষেপ বলে দেয়

| ❌ Message | ✅ Message |
| --- | --- |
| "কিছু একটি ভুল হয়েছে" | "Model অনেক সময় নিয়েছে। যা তৈরি হয়েছে তা এই — আবার চেষ্টা করবেন?" |
| "Error 429" | "এই মুহূর্তে অনেক বেশি request। সাধারণত মিনিটখানেকের মধ্যে ঠিক হয়ে যায়।" |
| "আমি এতে সাহায্য করতে পারব না" | "আমি শুধু product documentation দেখি। Account-এর প্রশ্নের জন্য support-এ যোগাযোগ করুন।" |

একটি ভালো message-এর তিনটি অংশ: **কী হয়েছে, retry করা লাভজনক কিনা, আর আর কী চেষ্টা করা যায়।** এটা একটি model-এর জন্য
tool-এর error message লেখার শৃঙ্খলা, একজন মানুষের জন্য লেখা।
[Chapter ?? — Tool Calling ও Tool Surface](#ch-tool-calling) দেখুন।

একটি ব্যর্থ feature-এর উচিত সেই আচরণে ফিরে যাওয়া, যা product-টি এর অস্তিত্বের আগে করত। ব্যর্থ AI search keyword result
দেখায়। না থাকা একটি summary পুরো document দেখায়। **Inline একটি সহায়ক feature-এর ব্যর্থতা চোখে পড়া উচিত নয়।** যে editor
না পাওয়া একটি suggestion-এর জন্য error box দেখায়, সেটা কোনো suggestion না থাকার চেয়েও খারাপ।

### বিরক্ত না করে retry

আংশিক content ছাড়া একটি ক্ষণস্থায়ী failure একবার, নীরবে retry করুন। মানে একটি 500, বা প্রথম token-এর আগে একটি timeout।
Refusal বা content filter কখনো নিজে থেকে retry করবেন না। এটা একটি সিদ্ধান্ত, outage নয়, আর এতে আবার খরচ হয়। Manual
retry-তে প্রশ্নটা থেকে যেতে হবে। পরপর তিনবার ব্যর্থ হলে বলুন যে dependency বন্ধ।

> ⚠️ যে stream করা request ইতিমধ্যে token তৈরি করেছে, সেটা নিজে থেকে retry করলে দুবার charge হয়, আর দুটি আলাদা উত্তর
> জোড়া লেগে যেতে পারে। আংশিক state থেকে চালিয়ে যান, অথবা পরিষ্কারভাবে নতুন করে শুরু করুন, কিন্তু দুটি একসাথে নয়।

## কখন ব্যবহার করবেন

| Feature | বিশ্বাসের design | অগ্রাধিকারের failure state |
| --- | --- | --- |
| আপনার docs থেকে grounded উত্তর | Chunk id থেকে resolve করা inline citation | খালি retrieval আর refusal |
| Generate করা একটি draft | Accept করার আগে edit, সবসময় | Timeout, draft রেখে দিয়ে |
| Extract করা form field | পূরণ করুন, generate করা বলে চিহ্নিত করুন, undo রাখুন | নীরবে manual entry-তে ফিরে যাওয়া |
| লম্বা summary | প্রতিটি point তার source-এ link করুন | Truncation আর continue |
| Inline editor suggestion | চোখে পড়ার মতো চিহ্ন | নীরব ব্যর্থতা; কখনো বাধা দেবেন না |
| বেশি traffic-এর consumer feature | সোজাসাপ্টা উত্তর, ঢালাও disclaimer নয় | Rate limit, স্পষ্ট অপেক্ষার সময়সহ |

প্রথম screen-এর আগেই failure state-গুলো design করুন। এখানে এগুলো বিরল নয়, তাই এগুলো শেষে design করা মানে product-এর
বেশিরভাগটাই শেষে design করা।

## সাধারণ ভুল

**❌ একটি confidence percentage দেখানো**

> এটা পরিমাপের মতো পড়ায়, অথচ calibrated নয়। বদলে grounding দেখান।

**❌ Generate করা পরিবর্তন নিজে থেকে apply করা**

> নীরবে করা একটি ভুল edit যতটা বিশ্বাস নষ্ট করে, বিশটি ভালো suggestion ততটা গড়ে না।

**❌ ব্যর্থ হলে stream করা text মুছে ফেলা, বা কেটে যাওয়া উত্তরকে সম্পূর্ণ হিসেবে render করা**

> প্রথমটা ফেলে দেয় যা user ইতিমধ্যে পড়েছেন আর আপনি ইতিমধ্যে দাম দিয়েছেন। দ্বিতীয়টা অর্ধেক একটি বাক্য পাঠিয়ে দেয়,
> কারণ একটি `length` finish আসে HTTP 200-এর সাথে, আর কিছুই throw করে না।

**✅ Retrieve করা chunk id থেকে citation resolve করুন, আর ব্যর্থ হলে কী হয়েছে তা বলুন**

> বানানো একটি citation render হতে পারে না, আর পরের পদক্ষেপসহ একটি message একটি কানাগলিকে একটি action-এ পরিণত করে।

## 🔑 মূল শিক্ষা

- লক্ষ্য calibrated trust, সর্বোচ্চ বিশ্বাস নয়, আর অতিরিক্ত বিশ্বাসই দামি failure।
- দাবির সাথে জোড়া আর chunk id থেকে resolve করা citation যাচাই হয়, অথচ confidence score শুধু পরিমাপের মতো দেখায়।
- যা কিছু লেখে, সেটা একটি স্পষ্ট accept-সহ draft হওয়া উচিত, আর গ্রহণযোগ্যতা বাড়াতে undo নির্ভুলতার চেয়েও বেশি করে।
- Refusal, timeout, truncation আর rate limit স্বাভাবিক traffic, তাই আংশিক output রেখে দিন আর একটি `length` finish স্পষ্টভাবে ধরুন।
- ক্ষণস্থায়ী failure একবার, নীরবে retry করুন, কখনো refusal নয়, আর কখনো আংশিক stream-এর ওপর নয়।

## Interview-এর প্রশ্ন

**Q: উত্তর ভুল হতে পারে, এটা user-কে কীভাবে দেখান?**

বলে দিয়ে নয়, যাচাই করা সহজ করে। Citation দাবির পাশে বসে, আর retrieve করা ঠিক সেই অংশে link করে। Grounding সৎভাবে
জানানো হয়, আর সাধারণ জ্ঞান থেকে একটি সাবলীল উত্তরের জায়গায় আসে "আমি এটা খুঁজে পাইনি"। প্রতিটি message-এর নিচে একটি
disclaimer দায় সরিয়ে দেয়, অথচ কাউকে কিছু করার উপায় দেয় না।

**Q: একটি confidence score কেন দেখাবেন না?**

কারণ এটা দেখতে পরিমাপের মতো, অথচ পরিমাপ নয়। 80% চিহ্নিত উত্তরগুলো যদি মোটামুটি 80% সময় ঠিক না হয়, অনেক case-এ যাচাই
করে, তাহলে এটা শুধুই model-এর তৈরি একটি value। আরও খারাপ, নিখুঁত দেখতে একটি সংখ্যা একটি অস্পষ্ট সংখ্যার চেয়ে বেশি বিশ্বাস
বাড়ায়, তাই এটা user-দের অতিরিক্ত বিশ্বাসের দিকে ঠেলে দেয়।

**Q: কখন আপনি generate করা একটি পরিবর্তন নিজে থেকে apply করবেন?**

শুধু তখন, যখন ভুল ফলাফল তুচ্ছ, সাথে সাথে চোখে পড়ে, আর undo হাতের কাছেই আছে। দামি, চোখে পড়া কঠিন, ফেরানো যায় না, বা
অন্য মানুষকে প্রভাবিত করে, এমন যেকোনো কিছু একটি স্পষ্ট accept-সহ draft-এর মধ্য দিয়ে যায়। নীরবে করা একটি ভুল edit
user-কে প্রতিটি output যাচাই করতে বাধ্য করে, আর সেই ক্ষতি স্থায়ী।

**Q: Streaming-এর মাঝপথে request-টি rate-limited হয়েছে। User কী দেখেন?**

যে text ইতিমধ্যে এসেছে, সেটা রেখে দেওয়া আর অসম্পূর্ণ বলে চিহ্নিত, সাথে কী হয়েছে আর মোটামুটি কখন কাজ করবে, তার একটি
সোজাসাপ্টা note। Pane মুছে গিয়ে একটি সাধারণ error হয়ে যাওয়া চলবে না, কারণ তাতে ইতিমধ্যে পড়া আর ইতিমধ্যে দাম দেওয়া content
ফেলে দেওয়া হয়। আংশিক state থেকে চালিয়ে যাওয়াই প্রধান action, আর নতুন করে generate করা fallback।

**Q: কখন নিজে থেকে retry করেন?**

একবার আর নীরবে, আংশিক content ছাড়া ক্ষণস্থায়ী failure-এর জন্য: একটি 500, একটি overload, প্রথম token-এর আগে একটি timeout।
Refusal বা content filter-এর জন্য নয়, যেগুলো একই ফলাফল দেয় আর আবার charge করে। যে stream ইতিমধ্যে token তৈরি করেছে, তার
ওপরেও নয়, কারণ তাতে দুবার charge হয় আর দুটি উত্তর জোড়া লেগে যেতে পারে।

**Q: Failure state-গুলো আগে design করবেন কেন?**

কারণ এই ধরনের feature-এ এগুলো বিরল নয়, তাই এগুলো শেষে design করা মানে product-এর বেশিরভাগটাই শেষে design করা। একটি
সীমিত scope-এর assistant-এ refusal আর খালি retrieval রোজই ঘটে। এগুলো আগে sketch করলে একটি স্পষ্ট উত্তরও বেরিয়ে আসে: চমকপ্রদ
কাজটা করতে না পারলে feature-টি কী করে।
